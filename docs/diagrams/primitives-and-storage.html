Definition to Destination

Every generated thing in the game rests on two ideas: a primitive is one exact revision of a data-only definition, and a structure is a bounded ordered graph of instances that name those revisions. Drawn here as it actually stands, with every number read out of the live data root rather than the plan.

01 · the chain

One generator, one store, one reader

Authored content enters as templates and constraints, never as set members. The generator draws exact definitions from them and publishes a pack once; a versioned grammar composes those definitions into a graph; two player levers address one composed system. A new randomization level needs a vocabulary, a grammar and a presentation — no new storage, no new identity scheme, no new determinism argument.

02 · primitive-definition/1/registry/3

What one primitive is

  • Data, never an engine resource. A definition holds numbers, choices, colours and references. A mesh, a material or a texture is built from it by the engine adapter and is never itself the definition — which is what keeps generation engine-independent, enforced by a test that the core assembly references no Godot assembly.
  • Its category declares its shape. The category registry names every category and, per category, its parameters in order, its connector kinds, and the storage policies it permits. The registry is itself a canonical record with a version and a hash, so a definition is only ever read under the revision it was written for.
  • Its parameters are typed and exact. A bool, a choice from named labels, an integer in a declared unit, a binary turn, a rotation, a three-vector, a colour, or a reference to another primitive of a named category. No floating-point value reaches a stored record, and a quantity that follows from others is not drawn at all — it is derived by a named rule.
  • Its identity is its content. The SHA-256 of its canonical encoding is its name. Two definitions with the same bytes are the same primitive, and every reference carries both the pack-local id and the hash, so it either resolves to exactly what was meant or fails.

A revision may add to a category without invalidating the older one, and a record of an earlier revision keeps its bytes and therefore its hash. That is how these grew: revision 2 replaced the parameters that could contradict themselves with derived ones; revision 3 gave a planet the material its surface is made of and let a definition carry tags of its own; and revision 4 puts what a stored quantity means into the record — a unit as a base symbol and a decimal exponent, a default wherever the kind admits one, the decoder’s validation bounds, a full descriptor on a derived parameter, and a barycentre’s mass as the first aggregation rule. The fault it answers is inside revision 3: mass appears on three categories in two different units, and nothing in the bytes said which. This build loads all four revisions side by side, a pack published under revision 1 still reloads today, and the two packs in this data root remain revision 2 and revision 3 records. Every category permits one storage policy so far, materialize, of the three the model admits.

03 · template-vocabulary/1

Where definitions come from, and what a tag answers

A vocabulary states templates — a category, a label, a range per parameter, the tags a definition carries, the tags a reference demands, and the tags a connector provides and requires — and how many definitions of each template a set should hold. Authored content enters here and nowhere else; in the core release a set holds generated definitions only.

04 · composition-graph/1 · grammar 4 over registry 3

What a primitive-based structure is

A structure is a composition graph: a bounded, ordered tree of instances. It is not set membership — an instance may repeat a definition, and order is meaningful. Each node names one exact definition revision, carries the transform that attaches it to its parent, and holds its children grouped by connector kind in the category’s order. A transform’s type follows from the connector it hangs on: OrbitalElements for a body orbiting a body or a barycentre, Rigid for a part bolted to a part, SurfaceAnchor for a region pinned to a planet.

Every instance has a stable canonical path, whose first segment is the domain and whose later segments name the connector it hangs on and its index among that connector’s children. That path addresses the instance’s random stream, its overlay records and its cache entries; it cannot drift, and the graph record refuses one that does.

05 · exact references

What pins what

An identifier alone cannot name usable content. Every reference carries a pack-local id and a content hash, and every record pins the exact revision of what it was built from, so a chain of four records either resolves to precisely the bytes that were meant or fails at the first mismatch.

06 · the data root

Where it all lives

Player data never lives in the repository or the install directory. Persistence owns one data root — ~/.local/share/SpaceExplorer on Linux, %LOCALAPPDATA%\SpaceExplorer on Windows, overridable with SPACE_EXPLORER_DATA_DIR — holding content-addressed record files plus one SQLite index. Caches live elsewhere and deleting them never loses a discovery.

<data root>/
  index.db                                  SQLite: verified packages, graphs, destinations, and the edges of their dependants
  packs/<pack-id>/<content-hash>.bin        immutable records, shared by every campaign
  blobs/<content-hash>.bin                  immutable mesh, texture, and primitive-owned payload data
  campaigns/<branch-id>/campaign.db         campaign state, transaction ledger, destination index  (not built yet)
  campaigns/<branch-id>/worlds/<spec-hash>/ world package: manifest, root graph, chunks         (not built yet)
  backups/<branch-id>/                      rolling recoverable copies of campaign.db           (not built yet)
<cache root>/
  compositions/, meshes/, textures/, collision/  rebuildable, size-limited, fully evictable          (not built yet)

The index holds identity and topology only — no parameters, no geometry, no environment properties. Canonical binary files stay authoritative, so losing index.db costs a rescan of the manifests, never a stored world.

07 · the same machinery, waiting for its vocabulary

What is drawn here, and what is not built

The registry admits seven composition domains. Three carry the randomization levels the game needs, and the rest are the same generator, the same store and the same reader awaiting a vocabulary and a grammar — which is the point of resting everything on one primitive.

  • World packages, overlays and caches are specified, not built. The composition chunk, the primitive-state overlay keyed by instance path, the eviction rules and the deletion sweep all have their contracts written and no code behind them yet.
  • Cross-package set algebra is deliberately unimplemented. Union, intersection and difference over exact references are specified, and the interface sits in the core unimplemented until a feature consumes them.
  • One storage policy is in use. Every category currently permits materialize only. regenerate and hybrid wait on measured throughput, and the choice is pinned by a manifest so that measuring never changes a definition’s hash.
  • A pair still contradicts its own masses. Registry revision 4 gives a barycentre the derived mass it always implied; placing the two companions by their mass ratio is a grammar’s work, and grammar 5 so far only restates grammar 4’s rules over the new registry. Nothing in this data root is composed under either yet.
  • The registry, the grammars and the numeric tables are code where the vocabulary is content. A template vocabulary is authored JSON that the generator reads; the registry and the grammars are C#. That asymmetry is a recorded, open finding, not a settled design.
  • Life is a structural absence. No category carries it, so the tier that requires it cannot be composed at all.
  • No performance target has been measured. Everything above is correctness and size, not speed.
