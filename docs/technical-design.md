# Space Explorer: technical design draft

Reviewed 2026-09-08. This is a proposed implementation contract for the [concept](concept.md). The [technology decision](technology-stack.md) selects Godot 4 .NET/C#, SQLite with `Microsoft.Data.Sqlite`, and Godot ENet as the working stack. No internet relay service is selected and no benchmark result is claimed. Requirements below apply to a future implementation.

## Architecture and ownership

The platform policy is fixed in [requirements.md](requirements.md). Its engineering consequences: keep the core generator and save format independent of operating-system APIs; pin compatible dependency versions for both platforms; package required runtimes and native libraries where their redistribution terms allow; define and test the supported OS/distribution, CPU, and graphics matrix rather than assuming one build runs on every Linux installation; and run Windows execution tests even when builds are produced on Linux.

Player data lives in the data root defined under [storage location and layout](#storage-location-and-layout), never in the install directory, and assets use portable relative paths. Test case sensitivity, path separators, native dependency loading, and save exchange between Linux and Windows. Network messages and saved data use explicit portable encodings rather than raw process memory layouts. The same campaign must remain compatible when a Linux host invites a Windows guest or vice versa.

Separate the deterministic generator, content registry, world store, campaign simulation, renderer, and network transport. Generation returns data independent of rendered frames or player input. Solo play uses the same command validation as hosted play. A texture recipe becomes pixels on the generator's side of that line: the named versioned rule `derive-surface-raster/1` computes an appearance's albedo image in the core by integer arithmetic over the appearance's own content hash, and the adapter only wraps those bytes ([decision 0056](decisions/0056-surface-raster-rule-and-the-boundary-of-stream-derivation.md)).

The domain, registry, and generation libraries use C# without Godot dependencies and serve both a command-line tool and the game; the repository is laid out by assembly ([decision 0009](decisions/0009-solution-layout.md)) and an architecture test asserts that the core assembly never references the Godot assembly. Keep database and engine APIs behind adapters. Worker tasks return plain data; apply scene changes through the Godot adapter on the appropriate thread. Core data and serialization contracts must not contain Godot node/resource references. Keep unsigned buffers in the core and use explicit, range-checked conversions at engine boundaries; engine serialization must not implicitly define the compact storage format.

The campaign owns credits, artifact custody, progression, destination references, and mutable primitive-state overlays. World packages own immutable specifications, complete primitive-composition graphs, and pinned dependencies. Memory and disk caches of derived exploration data can be evicted and rebuilt without changing discovery locations, simulation, or tradeable objects.

## Destination identity and determinism

A destination specification contains the campaign branch ID, a seed, distance tier, fixed content budget, and versions of the generator, registry, grammar, suit-validation profiles, and valuation rules; environment preferences and survey focus are not core fields, and the seed is filled by the dashboard's seed lever and never shown to the player as a number ([decision 0043](decisions/0043-destination-controls-distance-tier-and-seed-lever.md)). Define field ordering, numeric encoding, and units. A content hash identifies the specification. Because the branch is an input, the same seed produces a different system in another campaign and a system cannot be reproduced outside its discoverer's campaign ([decision 0007](decisions/0007-artifact-collision-substitution-and-campaign-salt.md)).

Re-entering an existing specification in the same campaign selects that world's current state and never resets loot. The game's fork function assigns a new branch ID, copies existing worlds unchanged, and derives new destinations from the new branch; independent saves cannot export items into each other's economy.

Derive random streams from the seed and stable paths such as `system/planet/region/site/artifact`: SHA-256 over a canonical record of the world seed and the path's canonical UTF-8 bytes ([decision 0021](decisions/0021-sha256-stream-derivation.md)) supplies 128 bits, the low half seeding the PCG32 state and the high half, forced odd, selecting the stream. Never hash the path into the stream selector alone, because PCG32 streams over a shared state are not independent. Never use current time, frame count, thread scheduling, unordered iteration, or an unspecified language hash as random input; the core project enforces this with a banned-API analyzer covering `System.Random`, `Guid.NewGuid`, `DateTime.Now`, `Environment.TickCount`, and `string.GetHashCode`. Adding optional details must not consume randomness from an unrelated artifact stream ([decision 0008](decisions/0008-random-stream-derivation.md)).

The working PRNG is PCG32 XSH-RR. Freeze its initialization, stream derivation, bounded sampling, integer overflow behavior, and reference test vectors under a generator version. Bounded integer sampling uses rejection, authoritative code never samples floating-point values, and the first reference vector is the PCG32 reference implementation's demo output for seed 42 and stream 54. Use canonical binary encodings and a specified content hash such as SHA-256, not runtime object hashes; the encoding format, its domain separation, and the rendered form of a hash are frozen by [decision 0020](decisions/0020-canonical-encoding-and-content-hash.md). Integer/quantized authoritative calculations and persisted accepted data limit floating-point variation; C# or a fixed seed alone does not prove cross-platform determinism.

Save the accepted complete primitive graph and its pinned inputs explicitly. Every authoritative property of the star, planets, orbits, interiors, surfaces, terrain, water, caves, vegetation and life, sites, artifacts, collision, traversal, physics, and behaviour originates in an exact primitive revision, its instance parameters, or the primitive-state overlay; manifests and graph topology introduce no parallel environment fields. Each category's policy, `regenerate`, `materialize`, or `hybrid`, is pinned by the world manifest, never by the definition ([decision 0034](decisions/0034-storage-policy-pinned-by-manifests.md)). Regeneration is permitted only when the retained generator revision reproduces exactly across supported platforms and measured background generation stays ahead of exploration; otherwise the accepted output is a primitive-owned materialized payload. Derived exploration products use fully evictable memory and disk caches. See [decision 0031](decisions/0031-primitive-complete-composition-and-storage.md), which supersedes the blanket materialization rule of decision 0001.

In the core release, determine all site and artifact recipes before accepting a destination; meshes and textures may load later. This makes reachability, predefined values, and uniqueness verifiable before play. Later region expansion must preserve these guarantees.

## Units, coordinates, and bounds

Authoritative quantities use the following versioned constants ([decision 0010](decisions/0010-units-coordinates-and-region-bounds.md)). Changing one is a generator or valuation version change.

| Quantity | Value |
| --- | --- |
| Length unit | Metre. Each frame below fixes its own position width and scale; no frame reuses another's by default ([decision 0036](decisions/0036-frames-and-transforms-typed-by-connector-kind.md)). |
| Frames | System inertial, planet-fixed, region-local, and artifact-local, all right-handed. The connector kind that attaches a node decides its transform type: orbital elements for an orbit connector, a surface anchor for a region, a rigid transform in the containing frame's position type otherwise ([decision 0036](decisions/0036-frames-and-transforms-typed-by-connector-kind.md)). |
| System inertial frame | Origin at the system root; +Z along its spin axis and +X toward its prime meridian at the epoch. Body positions are derived from orbital elements, never stored; distances are unsigned 64-bit metres. Orbital elements: semi-major axis in unsigned 64-bit metres, eccentricity as an unsigned 32-bit fraction of 2^32, inclination, node, periapsis argument, and mean anomaly at epoch as binary turns, epoch as simulation time. |
| Planet-fixed frame | Rotates with the body; +Z along its spin axis, +X through its prime meridian. Latitude and longitude as binary turns; reference radius and heights as signed 64-bit fixed-point at 1/256 m. Spin: pole direction as two binary turns in the system frame, sidereal period as unsigned 64-bit ticks, prime-meridian phase at epoch as a binary turn. |
| Region-local frame | Tangent frame at the region's surface anchor, latitude, longitude, height, and heading clockwise from north: +X east, +Y up, +Z south, origin at the region centre. Positions are int32 fixed-point at 1/256 m per axis; a stored or transmitted position is a region ID plus local coordinates. |
| Artifact-local frame | The artifact root's frame; positions are int32 fixed-point at 1/65,536 m per axis, range ±32,768 m. |
| Angle and rotation | A binary turn is a signed 32-bit value over 2^32 turn, range ±half a turn. A rotation is an intrinsic yaw, pitch, roll triple of binary turns about +Y, then +X, then +Z; stored, never integrated. |
| Region extent cap | 2,048 m per axis ([decision 0017](decisions/0017-region-extent-cap-and-storage-derivation.md)). Larger areas are adjacent regions. |
| Heightfield | 2 m cells; int16 heights at 1/16 m, a vertical range of ±2,048 m. A maximal region is 1,024 × 1,024 cells: 2 MiB of heights and 1 MiB of biome indices raw. |
| Simulation tick | Fixed host step at 20 Hz; durations in ticks; suit reserves and hazard exposure in integer units per tick. Simulation time is a signed 64-bit tick count since the world epoch. |
| Physical quantities | Mass, luminosity, pressure, temperature, and the like are integers or fixed-point with the width, unit, and scale declared per parameter in the category registry ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)); the numeric tables hold their ranges. |

Authoritative checks such as pickup range, reachability, and hazard exposure run on fixed-point values in the core. The Godot adapter converts to floats for rendering and physics; the region-local frame keeps those floats small. Double-precision engine builds are ruled out unless measurements force them.

## Astronomical state and surface sky

The authoritative system graph defines an inertial reference frame and epoch. Star and orbit primitives supply the central-body relationships, bounded orbital parameters, body radii or shape models, and the versioned propagation model. Each explorable planet supplies a spin-axis orientation, sidereal rotation period, and prime-meridian phase at the epoch, in the types of the [units table](#units-coordinates-and-bounds) ([decision 0036](decisions/0036-frames-and-transforms-typed-by-connector-kind.md)). The campaign overlay holds the saved simulation time. A region's surface anchor is a tangent plane at its latitude, longitude, and height, +Y outward, +X and +Z east and south rotated by the heading; the region is flat and its local frame is the observer's horizon frame, so the stellar grammar lands only on bodies of reference radius at least 524,288 m, the radius at which the true horizon from a 2 m eye height clears every corner of a maximal region. The ground between the region edge and the geometric horizon is a far field derived from the planet's cube-sphere relief grid, cached like the sky, with no collision or state; the region's traversal primitive declares its boundary, impassable in the core release with a displayed cue ([decision 0041](decisions/0041-planet-fields-tangent-regions-minimum-radius-and-far-field.md)). The time scale, pause rule, and inactive-destination advancement policy are versioned numeric configuration fixed before M1, never an implicit read of wall-clock time ([decision 0032](decisions/0032-astronomically-consistent-surface-sky.md)).

For any observer and simulation time, Core computes celestial body positions in the inertial frame, transforms them through the rotating planet-fixed frame into the local horizon frame, and derives direction, range, angular radius, illumination geometry, and occlusion state. The renderer uses one result for both the star disc and its directional light. A generated body is rendered only when it is above the geometric or atmosphere-adjusted horizon and meets versioned apparent-size or brightness thresholds. Phase and illuminated-limb orientation follow the star-body-observer geometry; solid bodies participate in eclipses and occultations. The renderer never hard-codes a body's direction, size, phase, count, or visibility. Non-explorable bodies are seen only in this sky at their derived angular size and phase; the core release has no approach, telescope, or orbital view, and a body's disc appearance derives from its planet and atmosphere primitives, whose planet-domain surface materials are added at M0b ([decision 0045](decisions/0045-close-views-only-in-the-surface-sky-and-a-derived-system-description.md)).

Background-star directions, colours, and brightness are pinned generated world data in the inertial frame, so they traverse the local sky with planetary rotation. A bounded generated field is sufficient; reproducing a real stellar catalogue is not required. Atmosphere primitives choose approved bounded models for scattering, extinction, twilight, and any refraction included in the visibility calculation. The explicit airless-atmosphere primitive selects no scattering and no refractive horizon lift. Other generated sky contributors, including moons, rings, clouds, and weather, participate when present in the composition graph.

The core release uses a versioned deterministic analytic two-body propagation model, the generator revision identifier `propagate-two-body/1`: every periodic quantity is an unsigned 64-bit period in ticks and a binary-turn phase at the epoch, evaluated exactly as `phase0 + floor(((t - t0) mod P) * 2^32 / P)`, never an integrated rate; Kepler's equation is solved by a fixed iteration count with table-driven trigonometry; an orbit connector's parent is a body or an explicit non-rendered barycentre, and positions compose along the ancestry ([decision 0037](decisions/0037-derivation-rules-integer-periods-and-orbit-hierarchy.md)). Full n-body perturbations, scientific long-term ephemerides, and interactive orbital flight remain outside scope. Authoritative inputs, time, and reference outputs follow [decision 0031](decisions/0031-primitive-complete-composition-and-storage.md): if the propagation or trigonometric path cannot match across supported platforms, replace it with deterministic fixed-point/table machinery or materialize the bounded authoritative samples before M1. Godot may interpolate derived presentation values but never owns or advances the astronomical state independently.

## Generation lifecycle

Prerequisite: generate, validate, and durably publish reusable primitive sets as M0a work, using the registry contract below. Destination generation selects exact saved set manifests; it does not recreate primitive definitions from the current library on each journey.

The main sequence is `draft -> reserved -> generating -> validating -> ready`. Generation and validation may pause, fail, or be cancelled; paused work resumes its saved stage. A ready world can be revisited and never returns to draft.

1. Validate settings, equipment access, resource allowance, and content dependencies. Fix the seed and budget, then reserve travel payment atomically.
2. Generate the system and planet composition graphs, including star, orbits, planetary layers, physical properties, atmosphere, climate, radiation, and life primitives with documented parameters, deriving gravity, period, temperature, pressure, retention, tidal state, and orbit spacing through the derivation rules of [decision 0037](decisions/0037-derivation-rules-integer-periods-and-orbit-hierarchy.md). The system has exactly one star, the tier's planet and region counts from the numeric tables, life primitives only from the second tier, and a star of class F to M when the tier requires life ([decision 0044](decisions/0044-tiered-system-composition-one-star-and-explorability-by-validation.md)).
3. Generate deterministic region/chunk subgraphs for surfaces, terrain and relief, water and rivers, caves, biomes, vegetation and life, traversal, hazards, sites, artifacts, and return paths.
4. Validate the tier's required planets, one explorable planet at the starter tier and at least two explorable plus one life-bearing body above it, and reachable recovery routes against the declared suit profile. The counts and the star classes each tier demands come from the versioned tier profile, a canonical record the destination pins beside the suit profile, so a stored verdict can be re-checked against the rules that gave it ([decision 0058](decisions/0058-tier-rules-are-a-pinned-record.md)). The minimum landable radius is the versioned region-limits record, pinned beside them and printed in the description, so all four numbers a landing verdict rests on move only by a version ([decision 0059](decisions/0059-region-limits-are-a-pinned-record.md)). It supplies numeric gravity, pressure, temperature, radiation-dose, chemical-hazard, and mission-duration limits; a planet is explorable because a region on a body of at least the minimum landable radius passes them, never because of its body type ([decision 0044](decisions/0044-tiered-system-composition-one-star-and-explorability-by-validation.md)). A safe average planet temperature is insufficient.
5. Retry invalid structures deterministically up to a versioned attempt budget. Try a prevalidated fallback that retains all required constraints. If neither succeeds, fail explicitly and refund once.
6. Checkpoint completed work and stable task IDs or random-stream positions. Make the final package durable before publishing its manifest, settling payment, and exposing the destination.

The core cancellation rule refunds uncompleted reservations and retains the same specification for retries, so cancelling does not reroll a destination. Artifact locations and values are not revealed before readiness. Successfully prepared expeditions commit the charge even if the player later abandons exploration.

A system description, the star's spectral class and each planet's body type, explorability, and life in orbit order with their counts, is derived on demand from the accepted graph and never stored; the command-line tool prints it from a world package and the arrival screen shows it. It names no site, artifact, or value, and one fixed-seed description is a recorded vector ([decision 0045](decisions/0045-close-views-only-in-the-surface-sky-and-a-derived-system-description.md)).

Preparation duration is the real duration of the generation job; the job performs only useful generation work and is never padded to lengthen a wait ([decision 0004](decisions/0004-preparation-is-real-generation-time.md)). Pause at safe boundaries when resource limits are reached. Report completed work, remaining estimates, and validation failures. Every task needs a work or duration limit even inside a days-long expedition. Stop controls must remain responsive.

Closing the game saves progress and stops computation; restarting resumes durable work. A future optional worker must be explicitly enabled, resource limited, and coordinated with the campaign writer. Preparation can coexist with visits to ready worlds. Only one job may commit a particular destination.

## Primitive registry and composition

This section is the contract, field by field. For what a primitive and a primitive-based structure *are*, and why every generated level rests on the same two ideas, read [primitives.md](primitives.md) first.

| Field | Contract |
| --- | --- |
| `pack_id`, `primitive_id` | `pack_id` is a 128-bit identifier stored as a 16-byte BLOB: random once for an authored pack, derived from the canonical set specification hash for a generated pack, as its leading 16 bytes ([decision 0020](decisions/0020-canonical-encoding-and-content-hash.md)); a human-readable pack name is metadata only. `primitive_id` is a pack-local unsigned 32-bit ID (`uint` in C#). Reserve zero as invalid; allocate monotonically in stable order and never recycle identities. Authored packs persist an append-only allocation ledger; a generated pack allocates 1..n in generation order and needs no ledger. Reject overflow rather than wrapping ([decision 0006](decisions/0006-pack-identity-and-allocation.md)). |
| `content_hash` | The exact immutable definition revision. A generated definition has exactly one revision for life: its pack is published once, so `(pack_id, primitive_id)` names one hash, and any change flows through a new specification, a new pack, and new IDs. Revisions belong to authored template packs, where a compatible change to the same template retains its ID and receives a new hash and a different concept receives a new ID ([decision 0033](decisions/0033-generated-definitions-have-one-revision.md)). Every use pins both ID and hash; for a generated definition the hash verifies that the loaded content is the referenced content. A changed mesh, surface, connector, parameter schema, or rule is a new revision even if its filename is unchanged. |
| `category`, `domains` | The category is a stable numeric entry in the category registry, one canonical record `category-registry/N` shipped as authored data, defining the parameter schema, permitted connector kinds, storage-policy options, validation limits, and permitted generator revision identifiers; a definition record's domain label `primitive-definition/1/registry/N` names the revision its parameters are laid out under ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)). A primitive admits one or more broad composition domains such as solar system, planet, surface, cave, life form, site, and artifact. |
| `geometry`, `surface` | Engine-neutral procedural geometry or an exact mesh-asset dependency; separate exact primitives for visual geometry, collision and traversal. Every visible geometry primitive has a required surface-material primitive and optional texture primitives. Materials select approved shader templates with bounded deterministic parameters. |
| `parameters` | Typed ranges, units, defaults, and bounded variation from a closed schema, carrying from registry revision 4 the unit, the default where the kind admits one, and the decoder's bounds in the record's header [decision 0060](decisions/0060-registry-revision-4-units-defaults-and-validation-limits.md) specifies: booleans, enums, integers, fixed-point values/vectors/rotations/colours/bounds, exact primitive references, ordered arrays — the first of which, `RefList`, an ordered array of exact references to one category with a declared minimum and maximum length checked before allocation, arrives in registry revision 9 as a planet's palette of two to six biome elements ([decision 0070](decisions/0070-a-biome-is-a-derived-set-registry-revision-9-and-grammar-version-10.md)) — bounded rectangular grids, cube-sphere grids of six power-of-two faces for the planet domain ([decision 0041](decisions/0041-planet-fields-tangent-regions-minimum-radius-and-far-field.md)), and content hashes. No authoritative floating point, arbitrary JSON, unordered map, or engine type. A reference is constrained to a category, not to a domain, and a template's range for one may additionally demand tags of the definition it names, from which the generator fills it and nothing else, failing by name where the category holds no such definition ([decision 0055](decisions/0055-definition-level-tags-and-tagged-references.md)). |
| `connectors`, `constraints` | Typed connector role/direction, cardinality, attachment transform or spatial area, required/excluded tags, and parameter rules, where the connector kind fixes the transform type, orbital elements, surface anchor, or rigid transform ([decision 0036](decisions/0036-frames-and-transforms-typed-by-connector-kind.md)); plus parent/child, adjacency, environmental, scale, depth, count, and work constraints. Domain membership alone never proves compatibility. A tag is canonical text, unique in its list and at most sixteen to a list; from category-registry revision 3 a definition, and the template it comes from, may carry tags of their own beside their connector declarations, which is how a leaf category with no connector declares what it suits. A definition's tags answer a reference's demand at generation; a parent's connector requirement and a grammar band's demand are answered by the child's like-labelled connector declaration only ([decision 0048](decisions/0048-composition-grammar-version-1-graph-records-and-graph-publication.md), [decision 0055](decisions/0055-definition-level-tags-and-tagged-references.md)). |
| `storage_policy` | Not a definition field. The category registry lists the permitted options per category among `regenerate`, `materialize`, and `hybrid`; the world manifest pins the chosen option per category at generation time from versioned measured configuration, and the set manifest does the same for set-owned payloads, so measurement never changes a definition's hash ([decision 0034](decisions/0034-storage-policy-pinned-by-manifests.md)). Materialized data is a primitive-owned payload. |
| `dependencies` | Exact primitive revisions, content-addressed mesh/texture assets, and the generator revision identifier of the form `<generator>/<k>` that produces a `regenerate` or `hybrid` recipe ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)); missing or corrupt dependencies invalidate a pack. Runtime packages are data-only and cannot carry scripts, native code, or unrestricted shaders. |
| `provenance` | Kind of definition, which is `generated` for every core-release definition; author/source; generating template and set; recorded content reuse terms. Admitting other kinds is a manifest-format revision ([decision 0002](decisions/0002-primitive-set-content-gate.md)). |

The primitive-completeness invariant is normative: every rendered, simulated, physical, biological, environmental, and collectable property originates in an exact primitive revision, its generated instance parameters, or a primitive-based state overlay. Structural records carry identity, topology, versioning, storage, and integrity metadata only. Materials, textures, physical properties, behaviour, and aggregation rules are reusable primitives. Authored templates are separately versioned generation inputs rather than runtime primitives; generated definitions record their exact template revisions.

Two categories carry a required minimum for the core release. A **biome rule set** is a template vocabulary scoped to `biome element`; a **recovery challenge** is one scoped to `site component`, constrained to the return-path type and covering the route and challenge that [valuation](#artifact-valuation-and-transactions) scores as recovery effort ([decision 0026](decisions/0026-biome-rule-sets-and-recovery-challenges-are-template-vocabularies.md)). Neither is a new category, persistence record, or pipeline stage; both pass through the same generation, validation, and content gate as every other vocabulary.

### Primitive sets and compact references

A primitive definition is a typed reusable building block. A primitive set is an immutable, validated catalogue of exact primitive revisions plus its composition rules and dependencies; it is the first stored construction unit. A solar system, planet, surface, cave, life form, site, or artifact is instead a bounded ordered composition graph. Its nodes may repeat a definition and preserve their deterministic instance paths, parameters, transforms, connector edges, and child order. Nested graphs are acyclic and have versioned depth, node-count, and work limits.

Generate sets from a small authored vocabulary and explicit compatibility rules, not unconstrained random geometry. In the core release, sets contain generated definitions only; authored content enters as templates and constraints. Fix the seed, template versions, generator/grammar versions, count/work budgets, and the pinned base pack revisions; generate candidates in stable order; validate definitions and dependency closure; then commit the new pack with its accepted definitions, the set membership, and the set manifest together. Each generation run publishes exactly one new pack whose definitions receive IDs 1..n in generation order, so independent reproduction needs no shared allocation state. One `pack_id` names one manifest: a second manifest with a different hash under an existing `pack_id` is refused at publication as a reproduction failure ([decision 0039](decisions/0039-one-manifest-per-pack-identifier.md)). Bound retries and report exhaustion. Store the accepted output as well as the seed so loading does not depend on rerunning a changed generator. Publishing a changed set produces a new pack and set manifest rather than mutating a saved set.

The stable definition identity is `(pack_id, primitive_id)` and an exact reference adds the definition content hash. A `uint`, a `PrimitiveId` without its revision hash, or a truncated hash alone cannot identify exact usable content. A reference table rejects two entries with one `PrimitiveId`, since a generated ID has one hash ([decision 0033](decisions/0033-generated-definitions-have-one-revision.md)). Independently authored packs have distinct 128-bit namespaces without coordination, and revisions of one authored pack share its append-only ledger. Duplicate allocation fails validation. After `4,294,967,295`, creation needs a new pack; the expected scale is hundreds of definitions per set, thousands of explicit nodes per world, and derived instances bounded per node, the two counts measured separately ([decision 0038](decisions/0038-derived-instances.md)).

For one pinned pack revision, membership can be sorted, deduplicated `uint` vectors because the pack revision supplies every definition hash. For mixed packs/revisions, store an immutable reference table mapping package-local `uint` handles to exact references of `PrimitiveId` plus content hash; composition nodes use those handles. A handle is not a permanent primitive ID, and tables cannot be reordered in place. Union/intersection/difference across packages or revisions must resolve or remap exact references first; this rule is specified in M0a and the operations are implemented when a feature consumes them. This exact-reference rule supersedes the revision-blind code contract of decision 0029; the current `ReferenceTable` and set-operation interface must change before packages consume them. Preserve node order, repeated instances, transforms, parameters, and edges in composition graphs: graph nodes are not deduplicated set membership.

Every instance receives a stable canonical path whose first segment is its composition domain and whose later segments name the connector it hangs on and its index among that connector's children, as the implemented grammar produces: `solar-system/orbit/1/orbit/0` for the first moon of the second body, `artifact/attach/1/attach/0` for a part on a part. The path addresses its random stream, mutable overlay, cross-chunk references, and cache entries; it is not another allocated primitive ID. A category the registry marks as deriving instances produces them from the node's parameters and stream alone, addressed as `<node path>/item/<index>`, not stored as nodes, counted against the node's declared derived budget, and carrying parameters and a rigid transform but never children or connectors ([decision 0038](decisions/0038-derived-instances.md)). Versioned composition grammars use integer weights, eligible categories/connectors, required and optional children, count limits, semantic rules, bounded retries, and validated fallbacks. Each composed property has an explicit aggregation-rule primitive such as sum, weighted average, minimum, maximum, bounded composition, or override; insertion order never resolves a conflict implicitly. Physical relationships use derivation-rule primitives in the same position, each a generator revision identifier `derive-<name>/<k>` with typed inputs by instance path, one typed output, an integer or fixed-point implementation, and recorded vectors; the category registry declares a derived parameter computed on demand or stored and validated at load ([decision 0037](decisions/0037-derivation-rules-integer-periods-and-orbit-hierarchy.md)). An empty optional connector represents structural absence, while meaningful absence such as an airless atmosphere uses an explicit primitive.

Store packed vectors using a versioned format with explicit little-endian fields, lengths, and integrity checks ([decision 0020](decisions/0020-canonical-encoding-and-content-hash.md)). The canonical format is schema-driven, not self-describing: the bytes carry no field tags or types, so a reader dispatches on the record's domain label and must know that record's field order for the format version the bytes declare. A definition record's label carries the category-registry revision, so the reader selects the registry, then the category's parameter schema, before it allocates ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)). Reject invalid lengths, out-of-range handles, and resource-limit violations before allocation. Four-byte handles are a format detail: a million packed handles occupy 4,000,000 bytes (about 3.81 MiB), excluding headers, reference tables, parameters, assets, and runtime collection overhead, but expected packages hold thousands of handles, not millions. Do not allocate an array or bitset spanning the entire `uint` ID space.

Use SQLite metadata tables for indexed lookup and constraints, and BLOBs for compact vectors/recipes. SQLite INTEGER is signed and variable-width: bind primitive IDs as signed 64-bit values with a `1..4,294,967,295` range constraint, and store `pack_id` as a 16-byte BLOB. INTEGER is not a native four-byte unsigned column. The [technology decision](technology-stack.md#selected-components) records the supporting library/type references.

### Composition validation

Each world pins the exact set manifests, category registry, pack/primitive revisions, asset hashes, generator implementations, storage policies, and grammar revision it uses. Rules define integer weights, maximum depth, component count, and work bounds. Geometric compatibility and semantic validity are separate: connector-compatible pieces can still form an unreachable site or an artifact too heavy for every supported loadout. The grammar bounds an assembled artifact to 2 m in every axis, derives its mass by the `sum` aggregation rule over its parts, and assigns a size class from its bounds under the numeric tables ([decision 0046](decisions/0046-artifact-families-human-height-cap-cargo-by-mass-and-material-rarity.md)).

Before admitting packs, check unique IDs and exact revisions, complete hash-verified dependencies, supported category and parameter schemas, connector cardinality and compatibility, parameter ranges, graph and decoded-size bounds, finite recursion, data-only content restrictions, storage-policy support, and valid productions for required structures. Readers reject truncated, overflowing, non-minimal, trailing, or over-budget canonical encodings before allocation. Never resolve an old world against "latest" content.

Artifact identity uses the world identity and stable artifact path, with collision detection. For appearance comparisons, canonicalize the composition recipe, excluding instance IDs, names, invisible metadata, and irrelevant ordering, and bucket continuous parameters so near-identical recipes compare equal. A silhouette comparison from fixed viewpoints supplements recipe comparison as a near-duplicate detector and is first applied at the M0a content gate. Resolve duplicates within a new world using deterministic variation attempts in a fixed order.

Before committing a world, compare its appearance recipes with the campaign's existing artifacts. On a collision, re-sample only the colliding artifact from alternatives of the same family and tier budget, in a fixed order, from a variation stream salted by the campaign branch; geography, sites, and every other artifact are unchanged. Record each substitution as artifact path and variation index in the world manifest, so the world reproduces from its specification plus its manifest without replaying campaign history. Substitution precedes valuation. Validate uniqueness again at commit if jobs run concurrently. Only exhausted variation attempts reject the destination, with an explicit content-capacity error. Changing only a label does not create a distinct appearance ([decision 0007](decisions/0007-artifact-collision-substitution-and-campaign-salt.md)).

## Persistence and compatibility

| Record | Minimum contents |
| --- | --- |
| Primitive set | Set manifest identity, generation specification, the pack it publishes with its accepted definitions, category-registry revision and hash, grammar revision, pinned generator revision identifiers ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)), membership/exact-reference table, exact primitive and asset dependencies, storage policies for set-owned payloads ([decision 0034](decisions/0034-storage-policy-pinned-by-manifests.md)), provenance, and validation result. |
| Campaign | Branch ID, players, permissions, upgrades, catalogue, destination index, and the modified flag; credits and inventory/cargo are derived from the transaction ledger and cached. |
| World manifest | Specification identity, seed/inputs, pinned set manifests, exact primitive/asset and generator/grammar dependencies, root composition reference, chunk index, variation overlay, the pinned storage policy per category ([decision 0034](decisions/0034-storage-policy-pinned-by-manifests.md)), and validation result. It contains no independent environment properties. |
| Composition graph/chunk | Ordered primitive instances with stable paths, exact-revision handles, generated parameters, transforms, typed connector edges, child order, and primitive-owned materialized or hybrid payloads, which under `materialize` or `hybrid` include a node's accepted derived instances as a bounded ordered array ([decision 0038](decisions/0038-derived-instances.md)), the first being `region-payload/2`, which carries a region's biome patches beside its heights ([decision 0070](decisions/0070-a-biome-is-a-derived-set-registry-revision-9-and-grammar-version-10.md)). Large surfaces use deterministic independently addressable chunks. |
| Artifact | Stable artifact path and root composition reference, origin, valuation inputs/version, and predefined value; appearance and physical properties come from its primitive graph. |
| Mutable state | Primitive-state overlays keyed by stable explicit or derived instance path ([decision 0038](decisions/0038-derived-instances.md)) for discoveries, pickups/custody, damage, depletion, field caches, annotations, and claimed survey rewards. |
| Transaction | Unique command ID, state revision, validated inventory/credit changes, committed result, the previous row's tag, and this row's integrity tag. |
| Generation job | Specification, reserved charge, completed tasks, checkpoints, progress, and failure state. |
| Reference index | One row per dependant, a campaign, world, export, or backup, per package or blob it depends on; inserted in the publish-last transaction, rebuildable by scanning manifests, and the input of the explicit deletion sweep ([decision 0040](decisions/0040-reference-index-and-deletion-sweep.md)). |

Canonical binary package files are authoritative for definitions, graphs, parameters, dependencies, and primitive-owned payloads. SQLite stores indexed metadata for verified immutable packages and the transactional campaign overlay; derived immutable-package index rows are rebuildable where practical. Store recipes rather than every rendered polygon when exact regeneration meets the category policy, and compress materialized payloads as specified under [region encoding and compression](#region-encoding-and-compression). Memory and disk caches of generated meshes, textures, collision products, and chunks are size-limited and fully evictable. Never evict an authoritative graph, exact dependency, materialized payload, overlay record, or player action.

Inventory, artifact custody, and credits change in one atomic SQLite transaction through `Microsoft.Data.Sqlite`. A crash leaves either the old state or the committed new state, never a paid sale with an artifact still in inventory. Coordinate campaign writes, enable relational constraints, retain durable settings, and test failure recovery. External immutable primitive/world packages need a separate commit protocol: write and verify data first, publish database references last, and recover incomplete work on restart. A database transaction alone does not atomically commit external asset files.

Keep rolling recoverable saves and verify checksums on load. Low disk space pauses generation before endangering the active campaign. Archiving preserves both the world package and mutable state. Removing an archive is an explicit user operation with its loss of access explained. Shared packages and blobs are removed only by an explicit, user-confirmed sweep of zero-reference content; low disk space evicts caches and reports what a sweep would free but never sweeps ([decision 0040](decisions/0040-reference-index-and-deletion-sweep.md)).

Save format, generator, grammar, category-registry, and content versions are independent. A `regenerate` or `hybrid` primitive names a generator revision identifier listed by the category registry, and an implementation is retained for every identifier a supported registry revision lists ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)); a materialized primitive does not require rerunning its generator for authoritative output. Export includes the complete exact primitive, generator, grammar, and asset dependency closure; a seed alone is not a portable save. Export and migration serve the owner's backup and change of machine; a world is never transferred into another campaign ([decision 0005](decisions/0005-discoverer-hosts-every-visit.md)).

Migrate a copy, verify world identities and item/credit totals, and retain the original backup. Missing content causes a specific compatibility error; never substitute a current primitive or silently reroll a planet. Old worlds stay frozen by default. Applying new content requires a separately identified branch.

### Storage location and layout

Player data never lives in the repository or the install directory. Persistence owns a single data root: the operating system's local application data folder plus `SpaceExplorer`, which is `$XDG_DATA_HOME/SpaceExplorer` (by default `~/.local/share/SpaceExplorer`) on Linux and `%LOCALAPPDATA%\SpaceExplorer` on Windows. The environment variable `SPACE_EXPLORER_DATA_DIR` overrides it; tests use temporary directories. Rebuildable caches live under the cache root, `$XDG_CACHE_HOME/SpaceExplorer` (by default `~/.cache/SpaceExplorer`) on Linux and `%LOCALAPPDATA%\SpaceExplorer\cache` on Windows, and deleting them never loses a discovery. Roaming or cloud-synced profile folders are never used, because SQLite locking and multi-gigabyte world data do not tolerate them. Godot's `user://` directory holds engine settings and logs only; the command-line tool reaches campaign data without Godot ([decision 0018](decisions/0018-data-root-region-encoding-and-save-integrity.md)).

```text
<data root>/
  index.db                                            SQLite: verified immutable packages and blobs, and the reference index of their dependants
  campaigns/<branch-id>/campaign.db                   SQLite: campaign state, transaction ledger, destination index, generation jobs
  campaigns/<branch-id>/worlds/<specification-hash>/  world package: manifest, root graph, composition chunks
  packs/<pack-id>/<content-hash>.bin                  immutable primitive-set records, shared by every campaign
  blobs/<content-hash>.bin                            immutable mesh, texture, and primitive-owned payload data
  backups/<branch-id>/                                rolling recoverable copies of campaign.db
<cache root>/
  compositions/, meshes/, textures/, collision/       rebuildable exploration data, size-limited, evictable
```

Package and blob files are named by content hash, so identical data is stored once and every load verifies integrity before use. Publication writes to a temporary file in the target filesystem, flushes and re-reads it under all format and resource bounds, verifies its hash and dependency closure, atomically installs it without overwriting different content, and commits SQLite index references last. A set manifest whose `pack_id` directory already holds a manifest with a different hash is refused, reporting both hashes, and the index's uniqueness constraint on `pack_id` enforces the same rule at the commit-last step ([decision 0039](decisions/0039-one-manifest-per-pack-identifier.md)). That last transaction also inserts the reference-index rows for the manifest's dependency closure, so nothing is installed without its edges ([decision 0040](decisions/0040-reference-index-and-deletion-sweep.md)). Restart recovery ignores or removes incomplete temporary files and never exposes an unverified manifest.

### Region encoding and compression

A region has no parallel authoritative environment record: it is a deterministic spatial partition of the planet/surface composition graph, and every instance has one owning chunk. Planet-level relief, climate, insolation, and ocean datum are cube-sphere grids or recipes owned by the planet instance that regions sample ([decision 0041](decisions/0041-planet-fields-tangent-regions-minimum-radius-and-far-field.md)). Cross-chunk edges use stable instance paths, and generating one chunk never consumes another's random stream. For `regenerate`, the chunk stores graph inputs and pinned versions. For `materialize`, it stores accepted bounded grids or other payloads owned by primitive instances. For `hybrid`, it stores the compact authoritative level and regenerates higher detail. A region's heights are the first such payload: `region-payload/1`, a content-addressed record naming the rule and the relief-field hash that produced them, published into its graph's pack under the `Materialize` policy registry revision 8 permits the `region` category ([decision 0066](decisions/0066-generation-writes-to-the-database-and-the-view-only-reads.md)), and written when the destination is composed, after its graph and before its destination record ([decision 0067](decisions/0067-a-destinations-ground-is-generated-when-it-is-composed.md)). Its version 2 adds the region's derived set, the biome patches `biome-patches/1` draws from the region's own stream, under 640 B a region; the per-cell biome index is derived from the patches, the heights, and the planet's sea level on load by `derive-biome-index/1`, held in memory while a region is drawn, and never stored ([decision 0070](decisions/0070-a-biome-is-a-derived-set-registry-revision-9-and-grammar-version-10.md)), which is requirement R18's two tiers applied to one layer. The earlier heightfield encoding remains a benchmark candidate for a materialized terrain primitive: int16 heights at 2 m cells may use left/up prediction and zig-zag variable integers, and biome indices may use row run-length coding, with Brotli applied after canonical encoding. It is no longer the sole region format ([decision 0031](decisions/0031-primitive-complete-composition-and-storage.md), superseding that clause of [decision 0018](decisions/0018-data-root-region-encoding-and-save-integrity.md)).

Hashes cover decoded canonical primitive payloads, never compressed bytes. A maximal 2,048 m region's heights are 2,101,250 B raw and pack to a measured 0.35 to 1.26 MiB, mean 0.97, under a ceiling of 2.13 MiB that no ground the generator draws exceeds, the format itself admitting 2.26 MiB ([decision 0069](decisions/0069-decision-0068s-ceiling-is-the-generators-and-the-format-admits-18-bits.md)); the campaign budget is 640 MiB for 300 such regions, 292 MiB expected at the mean, derived from that ceiling rather than from decision 0017's assumed ratio ([decision 0068](decisions/0068-campaign-storage-budget-re-derived-from-the-payload-ceiling.md)). The biome adds a derived set and no per-cell map. Storage policy is selected per category: regeneration requires exact cross-platform output and measured background throughput that stays ahead of exploration; inability to prove either selects hybrid or materialized storage. Measure cold regeneration, warm-cache loading, memory, authoritative bytes, and cache bytes separately before freezing thresholds.

### Save integrity

Nothing stored locally can prove that the owner has not edited it; the measures below deter casual editing with a database browser or hex editor and no more ([decision 0018](decisions/0018-data-root-region-encoding-and-save-integrity.md)). Credits and artifact custody are derived from the append-only transaction ledger and cached, never stored as the only copy; an artifact's value is recomputed from its stored inputs under the versioned tables at load and at sale. Every ledger row, world manifest, artifact record, and persistent primitive-overlay record carries an HMAC-SHA256 tag over its canonical bytes, keyed by HMAC-SHA256 of the campaign branch ID under an application constant, and every ledger row includes the tag of the previous row so the chain cannot be rewritten piecemeal. At load the campaign verifies the immutable package hashes, overlay targets, chain, tags, and invariants: every artifact exists at an instance path in its world graph, each overlay targets a compatible explicit or derived instance, a derived path being resolved by evaluating its parent under the pinned generator revision and policy ([decision 0038](decisions/0038-derived-instances.md)), the value total of each world respects its tier bounds, and credits equal the ledger. Any failure sets the campaign's modified flag, which is itself tagged; the flag is shown to the host and to every guest at join and never locks the owner out. Extracting the key from the binary defeats the scheme, which is accepted; a public market remains a server-side problem.

## Artifact valuation and transactions

Recommended prototype rule, replacing literal elapsed-time pricing:

```text
base_value = round(k * (generation_effort + recovery_effort) * rarity_factor)
```

Generation effort is an authored per-tier base score plus a recipe complexity score computed from the composition graph, using node count, depth, and rare-connector use ([decision 0004](decisions/0004-preparation-is-real-generation-time.md)). Recovery effort is expected active effort from the site's route and challenge. Both are fixed before discovery in common reference-time units. The versioned coefficient `k` converts effort to credits; rarity is bounded, and a mineral material's rarity weight in the numeric tables feeds it ([decision 0046](decisions/0046-artifact-families-human-height-cap-cargo-by-mass-and-material-rarity.md)). Persist inputs and rounded value so later tuning does not reprice existing finds.

Illustrative values, not balance results: with `k = 10`, generation effort 4, recovery effort 6, and rarity 1.5, the base value is 150 credits. Taking twice as long to find it, pausing generation, or using a slower PC leaves that value unchanged.

Each tier also defines total artifact-value and artifact-count bounds. Validate the sum of prices so a full system-generation reward is not multiplied across arbitrarily many trivial items. Player preferences cannot set monetary coefficients.

The core uses fixed versioned dealer spreads; variable regional demand is deferred. For the example artifact, a dealer purchase offer of 120 and sale price of 180 prevents profitable immediate cycling. Buying it back restores custody of the same instance without resetting discoveries or rewards.

Optional capped survey bonuses pay once per newly completed objective and have a campaign claim ledger. Idling, retracing explored paths, and repeating scans do not earn them. They are separate from artifact prices. No real-money redemption is part of the concept.

Commands carry unique IDs. The authority checks location, reachability, capacity as a mass budget and a volume budget over each artifact's mass and size class ([decision 0046](decisions/0046-artifact-families-human-height-cap-cargo-by-mass-and-material-rarity.md)), ownership, permission, price, and expected state revision as relevant. Retried commands return their original results. Two players seeking one artifact yield one successful pickup; repeated sale requests yield one credit change. NPC trading changes custody and credits in the same transaction.

## Multiplayer and trust boundary

The core release supports a host and one guest in a private campaign; the session model, peer identity in commands, and per-peer avatars support additional guests up to a host-configured capacity, so adding guests is a capacity and testing question rather than a protocol change. The host is authoritative while also playing, and all simulation and generation compute happens on the host. Guest inventory and all progress live in the host's save. A discovered system is visited only in a session hosted by its discoverer; guests travel there with the host and cannot reach it on their own ([decision 0005](decisions/0005-discoverer-hosts-every-visit.md)). Credits and collection storage are shared; spending and selling require host permission. Guests can move, scan, and collect into their campaign inventory subject to validation. The host simulates suit reserves, hazard exposure, and emergency recovery for every avatar from client-reported positions and inputs at the fixed tick; clients predict locally for display only and never report reserve values, and the host is authoritative on reserve exhaustion, emergency recovery, and the field cache ([decision 0013](decisions/0013-host-simulates-hazards.md)). Transfers retain artifact identity and history.

A guest joins the host at the home anchor or at the host's single current destination ([decision 0012](decisions/0012-core-travel-model.md)). Joining exchanges protocol versions, peer identity, campaign identity, manifests, and state revision, and, from the first `regenerate` category on, the supported category-registry revisions and retained generator revision identifiers ([decision 0035](decisions/0035-category-registry-record-and-generator-revision-identifiers.md)). The host sends manifests and hashes first; the guest reuses locally verified blobs, obtains only missing data-only primitive packages/assets, verifies each before use, and then constructs or loads the required chunks under their pinned policies. Initial synchronization applies the mutable primitive-state overlay, including removed artifacts and committed state, separately from immutable content. Later updates carry ordered revisions and acknowledgments. State-hash mismatches trigger resynchronization.

Disconnecting never undoes hazards already applied: committed emergency recovery retains its field cache. Otherwise persist the guest's location and cargo and suspend that avatar; on rejoin restore it, keeping the ship return route available. Disconnect/rejoin must not duplicate items or provide free extraction. When the host exits, the session ends and resumes from its last durable state. Independent hosts cannot merge campaigns automatically.

The core defines the network contract: a byte transport with send, receive, peer-connected, and peer-disconnected, carrying commands, state deltas, and the join handshake serialized with the same versioned binary encoding as saves. This contract, its in-memory implementation, and its test suite are M0a work ([decision 0027](decisions/0027-in-memory-transport-commands-and-handshake-at-m0a.md)); the Godot adapter implements it over an ENet peer using raw packets at M1/M2. Godot's scene replication nodes carry only cosmetic presence such as avatar transforms, never authoritative state. The intended topology is a loosely coupled network of hosts coordinated by a simple cloud-based server that provides directory, invitation, presence, and relay or NAT-traversal assistance; it never holds campaign state or computes worlds. ENet itself does not supply a relay or solve all NAT restrictions, and a LAN demonstration is insufficient. The connectivity approach, account requirements, costs, and service-unavailable behavior are decided at M1 start, once a generated system can be explored locally from a stored save; a self-hosted relay and coordination server is evaluated first. The first mixed-OS host/guest connection runs at the start of M2 on the chosen path, in both host directions. Solo play remains usable offline, and direct connection by address remains available when the coordination server is unreachable. See [decision 0003](decisions/0003-network-topology-and-transport.md).

Bound message and package sizes, graph depth and node counts, connector edges, arrays/grids, mesh/image complexity, and decompressed data before allocation. Primitive packages are data-only: guests and imported worlds cannot supply executable scripts, native libraries, or unrestricted shader programs. Checksums detect corruption, and the tagged records and chained ledger under [save integrity](#save-integrity) deter casual editing, but neither proves that an offline owner has not edited a save; a modified campaign is disclosed to guests at join ([decision 0018](decisions/0018-data-root-region-encoding-and-save-integrity.md)). Private host trust is sufficient here. A future public market requires a separate server-controlled ownership model and cannot trust arbitrary offline inventories.
