# 0035. The category registry is a versioned canonical record that definition labels carry; generator revisions are identifiers it lists

Date: 2026-09-07. Status: Accepted. Source: review recommendation taken on the owner's instruction of 2026-09-07 to follow the recommended path.

## Context

The canonical format is schema-driven, not self-describing ([decision 0020](0020-canonical-encoding-and-content-hash.md)): a reader dispatches on a record's domain label and must know the field order for the version the bytes declare. A definition's parameter payload is laid out by its category's parameter schema, so no reader can decode a definition without the category-registry revision that defined it, yet no document said where the registry lives, how its revision is named, or which record carries it ([review finding 34](../review.md#34-the-category-registry-has-no-home-no-revision-identity-and-no-stated-role-in-decoding)). Separately, a `regenerate` or `hybrid` primitive "pins its generator implementation, which remains available while anything references it", but nothing named that implementation: the only generator identity was `GeneratorVersion`, one integer covering the random foundation alone ([decision 0021](0021-sha256-stream-derivation.md)), and the join handshake of [decision 0028](0028-in-memory-transport-command-and-handshake-contract.md) compared protocol versions only ([review finding 33](../review.md#33-the-generator-implementation-a-regenerate-primitive-pins-has-no-identity)). Both had to be fixed before the `PrimitiveDefinition` record of the M0a immediate step.

## Decision

**The registry is a canonical record.** The category registry is one canonical record with domain label `category-registry/N`, where `N` is an integer revision starting at 1, encoded under [decision 0020](0020-canonical-encoding-and-content-hash.md) and identified exactly by its content hash. It is authored data under `content/` and ships with the game and the command-line tool; its authored source form is a tool concern, the canonical record is the authority. A registry revision is immutable: any change is revision `N+1`. Per category it records the stable numeric category ID with zero reserved, a stream-path-form label, permitted composition domains, the ordered parameter schema with each parameter's type, width, unit and scale, range, and default, permitted connector kinds, permitted storage policies ([decision 0034](0034-storage-policy-pinned-by-manifests.md)), validation limits, and the generator revision identifiers that may produce it.

**Definition labels carry the revision.** A definition record's domain label is `primitive-definition/1/registry/N`, so the reader selects the registry revision before it reads a field, then reads the category ID and selects the parameter schema before allocating anything. Two definitions with identical fields under different registry revisions therefore never share a hash, as decision 0020 requires of records of different kinds. Every pack manifest pins the registry revision and content hash it was generated under, and a pack whose pinned hash differs from the game's copy of that revision is refused. The game lists the registry revisions it supports and refuses any other with a compatibility error naming the revision, never by substituting a schema.

**Generator revisions are identifiers.** A generator revision identifier is a stream path of the form `<generator>/<k>`, such as `terrain-heightfield/1`, with `k` an integer starting at 1. The registry lists, per category that permits `regenerate` or `hybrid`, the identifiers that may produce it. A definition's recipe names the identifier it is produced by, so the `dependencies` row admits generator revision identifiers beside exact primitive revisions and asset hashes; a different identifier is a different definition. Set and world manifests pin the closure of identifiers they used. The game retains an implementation for every identifier any supported registry revision lists; dropping one is a registry revision, and content that pins a dropped identifier fails with a compatibility error, never a substitution. Retention is per identifier, not per whole generator. `GeneratorVersion` stays what it is, the version of the random foundation, pinned separately.

**The handshake advertises both.** The join handshake gains the guest's supported registry revisions and retained generator revision identifiers, so a mismatch fails before any package moves. It is added as a `ProtocolVersion` increment under decision 0028 when the first `regenerate` category exists, not before.

## Consequences

Easier: a definition's bytes are decodable from its label alone plus a shipped data file; an unsupported registry or generator is a named error at the first read rather than a wrong decode; the generator that made a definition is part of its content, as the content it produces requires. Harder: every parameter schema change is a registry revision that every later pack pins, and the retained-implementation set grows with every identifier a supported registry lists, so retiring one is a deliberate registry revision. Verified by the Primitive-set foundation, Compatibility, and Multiplayer checks in the [development plan](../development-plan.md#verification-and-performance-targets).
