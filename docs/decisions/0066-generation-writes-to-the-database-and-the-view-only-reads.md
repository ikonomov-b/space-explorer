# 0066. Generation writes to the database and the view only reads, so a visited surface is stored in full detail

Date: 2026-09-11. Status: Accepted. Source: the owner's instruction of 2026-09-11, given while reading surface cycle three: "for the next iterations start storing the generated planet surface locally and fully load it from the db, before showing it in 3d", "the generation randomization process should be directed to db, not to direct rendering", and, on what is kept, "the whole environment should be stored locally, because the travel destination solar system and its explorable planets should be available for multiple visiting and exploration continuation", refined to "eventually only the once visited areas could be stored in a full detail". Supersedes clauses 9 and 10 of [decision 0063](0063-relief-by-terrain-heightfield-registry-revision-6-and-grammar-version-7.md) — the region's regenerate-only storage policy, and the deferral of the payload record class — and nothing else of it.

## Context

Today the renderer generates. `SurfaceView` builds a `relief-field` in its constructor, calls `terrain-heightfield/2`, and draws the samples it gets back; nothing of that ground is written anywhere, and the next run computes it again. A stored destination does reload without composing — its graph, its set, its anchors and its relief parameters all come off disk — so the surface is *reproducible* from the database. It is not *in* the database.

[Decision 0063](0063-relief-by-terrain-heightfield-registry-revision-6-and-grammar-version-7.md) chose that deliberately and its arithmetic was right as far as it went: a body of the minimum landable radius holds some 823,500 maximal regions, so materialising a whole planet's surface costs 804 GiB against the 300 MiB [decision 0017](0017-region-extent-cap-and-storage-derivation.md) budgets a campaign. What that arithmetic bounds is storing every region a planet *could* have. It says nothing about storing the regions a player actually stands on, and those are a different quantity entirely: a destination under grammar version 8 carries one region per admitted body, which is five on the sample's median system — some 10 MB of ground for a whole solar system.

Two things follow, and the owner named both. A destination is a place revisited rather than a picture taken once: [decision 0043](0043-destination-controls-distance-tier-and-seed-lever.md)'s levers name it, [decision 0004](0004-preparation-is-real-generation-time.md) charges real time to prepare it, and an expedition is meant to be continued. And detail is worth keeping only where someone has been.

**What this record does not rest on, having measured it.** The obvious argument for storing a surface is that regenerating one is slow, and that argument is false here. A maximal region regenerates in 53 ms warm and 322 ms on the first call of a cold process, in a release build on the reference workstation — independently measured at 43 ms and 311 ms by a second reading of the same code the same day. Reading a stored payload back is not free either: it is a SHA-256 verification of a megabyte plus a bit-unpacking pass. Asked directly whether he still wanted a store given those numbers, the owner said he did, and not for speed: regeneration is acceptable to him "as soon as the visible distance is loaded fast enough and is unchanged from the previous visit", and both of those already hold.

So the case is the one that survives the measurement, and it is worth stating plainly because the tempting case does not. **First**, a renderer that generates is a second implementation of the world: it can draw what is not stored, and nothing catches the divergence. [Decision 0031](0031-primitive-complete-composition-and-storage.md) requires the content-gate viewer to resolve stored primitives rather than choose its own, and a view that reads is that viewer one level earlier than the gate needs it. **Second**, a stored surface is stable against its own rule. `terrain-heightfield` has gone to a second version once already, on a fault a reading found; when a third version lands, a regenerating view silently redraws every previously visited place, where a store keeps what was visited as it was and makes the difference visible instead. That is what "unchanged from the previous visit" buys once the rules themselves start moving, which regeneration alone cannot promise across a version.

## Decision

**1. Generation writes to the database; the view only reads (open; the owner's instruction).** The 3D view resolves a region's ground by loading its stored payload, and calls no generation rule. Where no payload exists, the *generation* step produces and publishes one, and the view then loads what was published — so the picture is always of stored bytes, and there is no path by which what is drawn differs from what is kept. This is what [decision 0031](0031-primitive-complete-composition-and-storage.md) asks of the content-gate viewer one level earlier than the gate needs it, and it removes the standing risk that a renderer and a store disagree about the same world.

**2. `region-payload/1`: the primitive-owned payload record class (follows from clause 1; supersedes decision 0063 clause 10).** A canonical record under [decision 0020](0020-canonical-encoding-and-content-hash.md), content-addressed like every other, carrying: the region's instance path; the identifier and version of the rule that produced it; the content hash of the `relief-field` it was produced from; the extent and the samples across; and the int16 heights in the order `terrain-heightfield` gives them. Its own content hash names its file, so a payload is verified against its name on load exactly as a definition is, and a corrupted one is refused rather than drawn.

It is indexed under the graph's pack, because a region is a node of that graph ([decision 0063](0063-relief-by-terrain-heightfield-registry-revision-6-and-grammar-version-7.md) clause 4) and its ground belongs to the same world. This is the record class [primitives part 5](../primitives.md#where-it-must-grow) has named as missing since the storage assessment, arriving with the first thing that needs it.

**3. Full detail is stored for visited ground, and kept (open; the owner's rule).** A region's payload is written when that region is first generated, and it is not evicted. What bounds the store is therefore where a player has been, not what a planet could hold: unvisited ground costs nothing because it is never produced, and visited ground is paid for once. This is [decision 0034](0034-storage-policy-pinned-by-manifests.md)'s `Hybrid` exactly — materialised, and reproducible by a named rule if it is ever lost — and registry revision 8 declares it so, keeping the generator revision listed because the bytes have a producer that can still make them.

No eviction rule is written here, because at one region per body nothing yet approaches a budget, and an eviction policy no measurement informs is the scaffolding [decision 0024](0024-tests-comments-index-and-scaffolding-trimmed.md) refuses. What it owes instead is a number: the Resource-use row records what a destination's stored ground actually costs, which is the first real figure that check has ever had.

**4. Registry revision 8 and grammar version 9 (follows).** Revision 8 is revision 7 with the `region` category's permitted policies widened from `Regenerate` to `Regenerate | Materialize`, its generator revisions unchanged. Grammar version 9 lays version 8's rules over it and adds no production. Revisions 1 to 7 and versions 1 to 8 stay supported, so cycles one to three reproduce from their records.

**5. What is not stored, and why that is not a contradiction (follows).** The `relief-field` record is still derived rather than written: it is six small numbers a planet already stores, and writing it would store the same bytes twice under two names. The payload names its field by hash, which is what makes a stored surface checkable against the content it claims to come from — if a planet's relief parameters change, the field hash changes, and the stored payload is visibly of another world rather than silently of this one.

**6. What proves it (follows).** A payload published and reloaded byte for byte; a view that draws a region loading a payload and calling no rule, which is clause 1's whole claim and is tested by the rule's absence from the view's path rather than by a picture; a payload whose bytes do not hash to its name refused by name; two processes publishing byte-identical payloads for one region, as [decision 0048](0048-composition-grammar-version-1-graph-records-and-graph-publication.md)'s graphs already are; a payload naming a field hash the graph does not derive refused; and the cost of a destination's stored ground recorded.

## What this does not settle

| Deferred | Needed at |
| --- | --- |
| Compression, which [decision 0017](0017-region-extent-cap-and-storage-derivation.md) assumes in budgeting 1 MiB against a 2 MiB raw region and which no record format has today | When a destination's stored ground is measured against the campaign budget, which clause 3 asks for now |
| Eviction, its key and its policy, which [decision 0031](0031-primitive-complete-composition-and-storage.md) requires of regenerated content | When a planet carries many regions or chunks, which is rung 7 |
| What a player *changes*, as against what was generated: the mutable-state overlay of [decision 0038](0038-derived-instances.md), which this record's payload class is a prerequisite for but not an instance of | When there is a player |
| Whether a partially explored region stores partially, which is the same question one level down and which chunking answers | Rung 7 |

## Consequences

Easier: what is drawn and what is stored cannot diverge, because they are the same bytes; a visited surface survives a change to the rule that made it, which is the one sense in which a revisit is guaranteed unchanged; the payload class [primitives part 5](../primitives.md#where-it-must-grow) has wanted since the storage assessment exists, and the mutable-state overlay now has something to be modelled on; and the Resource-use check gets its first real measurements instead of a derivation — both what a destination's ground costs on disk and what regenerating it costs in time.

Harder: an eighth registry revision and a ninth grammar version join those retained, and this is the fourth rung-scale change to fire [finding 54](../review.md#54-the-registry-the-grammars-and-the-numeric-tables-are-code-where-the-vocabulary-is-content)'s trigger; a destination's records grow from kilobytes to megabytes, so the data root stops being something to ignore; publishing a destination now costs the generation of every region it carries rather than of none, which moves work from first view to first publish; and decision 0063's reasoning must be read with this record beside it, since its arithmetic is sound and its conclusion is superseded.

**What must be verified**, on the evidence [progress](../progress.md#surface-iterations) records: registry revision 8's and grammar version 9's frozen hashes beside the earlier ones, every earlier hash unmoved; the six checks of clause 6; and the exported-build smoke check still printing `SMOKE OK`.
