# 0053. A destination is a stored record addressed by its levers, and the view draws what is stored

Date: 2026-09-10. Status: Accepted. Source: the owner's instruction of 2026-09-10 to store a generated solar system in the primitives database as a set of primitives, read it back from there, and show it in three dimensions, and the owner's choice the same day that a composed destination gets a record of its own now rather than waiting for the world manifest of M0b.

## Context

A generated system is already stored as primitives. `compose` publishes one canonical graph record whose every instance is a varint naming an exact definition revision of the pinned set, a transform, and its child counts ([decision 0048](0048-composition-grammar-version-1-graph-records-and-graph-publication.md)), and reading it back exists too: `inspect-graph`, `validate-graph`, and `describe` load the record and derive from it. The records are small, because the variety lives in the set every system shares: a 27-instance system is 764 bytes and a 3-body one 210, over a set of 94 definitions in 17.5 KB.

What is not stored is the destination. [Decision 0052](0052-the-two-levers-compose-a-destination-and-a-review-view-shows-it.md) composes one from the two levers of [decision 0043](0043-destination-controls-distance-tier-and-seed-lever.md) by bounded retry, and both the `destination` command and the review view throw the result away: nothing maps a lever pair to the attempt that won, so a system that was reviewed, or played, can only be found again by composing up to sixty-four systems, and the view cannot draw a stored system at all. Nothing therefore proves that what is drawn is what is stored, which is the property the world of M0b will be read through.

## Decision

**A destination is addressable before it is composed.** A destination specification is a canonical record under the domain `destination-specification/1` holding the tier, the lever seed, the generator version, the category-registry revision and hash, the grammar version and hash, the source set's pack identifier and manifest hash, the system-description version, and the suit profile's version and hash. The leading 16 bytes of its content hash are the destination's pack identifier, as for a set and a graph ([decisions 0006](0006-pack-identity-and-allocation.md), [0020](0020-canonical-encoding-and-content-hash.md)). Every field is known from the two lever values and the build's own pins, so the pack identifier follows from the levers alone: finding a stored destination is a content-address lookup rather than a search or an index query.

**The record holds that specification inline and the result beside it**: the winning attempt, the composition seed, and the graph's pack identifier and hash. It is published through the protocol sets and graphs already use ([decision 0042](0042-category-registry-revision-1-first-content-records-generator-and-publish-protocol.md)): the graph must already be published and hash to what the record names, the record is written to a temporary file, verified, and moved into place, the index is committed last, and one record per pack identifier is the rule, a second differing one being refused before anything is written ([decision 0039](0039-one-manifest-per-pack-identifier.md)).

**The index gains a `destinations` table** beside `graphs`: the pack identifier, the record hash, the graph's pack identifier, the tier, the lever seed, and the attempt, with dependant rows tying a destination to its graph and a graph to its set, so the deletion sweep of [decision 0040](0040-reference-index-and-deletion-sweep.md) has an order to delete in. The table is an index and not the identity: it holds nothing that the published records do not, and is rebuildable from them.

**The levers read before they compose.** `destination --tier <name> --seed <n>` computes the pack identifier from the levers and the pins, loads the stored record and its graph when one is there, and composes, publishes, and prints when there is not. The bounded retry of decision 0052 is therefore paid at most once per lever pair. `--no-publish` keeps a sweep of many seeds out of the data root, which is what `iterate` needs.

**The view draws what is stored.** `--system --destination <pack>` loads a stored destination, its graph, and the set it pins, and draws that; `--system --tier <name> --seed <n>` composes the destination the levers name, publishes it, and draws that. Both derive the description from the stored graph under the pinned description version, so a picture and a record cannot disagree, and the path the view reads through — loader, registry, derivation, draw — is the one the game reads through at M1.

**Nothing derived is stored at the system level.** A body's radius, surface gravity, equilibrium temperature, and its line of the description are derived on read from the stored parameters under the pinned description version and suit profile, which is the `regenerate` policy of [decision 0034](0034-storage-policy-pinned-by-manifests.md) stated rather than left to silence. The evidence is that derivation is not the cost at this scale: describing a stored 27-instance graph, composing and publishing the same graph, and composing a three-attempt destination take 0.144, 0.164, and 0.168 seconds of wall clock as separate processes, all of it dominated by about 0.1 second of .NET startup. A `materialize` or `hybrid` policy for a level whose measurement says otherwise, region and terrain payloads first, remains open under decisions 0031 and 0034.

## Consequences

Easier: a lever pair names a stored system on any machine, so what was reviewed can be reopened, cited in an iteration record, and drawn without composing; the review harness and the game read one pipeline out of the database into the view; the world of M0b has its shape already, a world manifest pinning a destination, a destination pinning a graph, a graph pinning a set, with region and terrain payloads hanging off nodes as primitive-owned payloads by the same rule ([decisions 0031](0031-primitive-complete-composition-and-storage.md), [0038](0038-derived-instances.md)).

Harder: this is another frozen content format landing before the still-required P0 exit record, whose compatibility cost the owner has already accepted once ([decisions 0022](0022-p0-gates-the-first-frozen-content-format.md), [0030](0030-m0a-criterion-1-proceeds-before-the-p0-exit-record.md)). Because the specification pins the description version and the suit profile, and both decide which attempt satisfies a tier, a new version of either reissues the destination pack for the same levers; the old record stays loadable and is swept when nothing depends on it. A data root now accumulates a small record per lever pair reviewed, which is what the sweep is for, and until the sweep exists they are deleted by hand.

Verified by tests that one lever pair yields one destination pack identifier and one record byte for byte on Linux and Windows, that a stored destination reloads without composing and a second run of the same levers composes nothing, that a record naming an absent or altered graph is refused, and that the view's stored path and its composing path draw the same graph hash; and by the Destination validity check of the [development plan](../development-plan.md#verification-and-performance-targets), which records the retry frequency the levers pay.
