# 0028. The in-memory transport, command journal, and join handshake contract

Date: 2026-09-07. Status: Accepted.

## Context

[Decision 0027](0027-in-memory-transport-commands-and-handshake-at-m0a.md) scheduled M0a exit criterion 15: define the core-owned byte transport, core commands with unique IDs and state-revision validation, and the join handshake, serialized with the same versioned binary encoding as saves, covered by a test suite over an in-memory transport. Nothing fixes the transport's exact members, how a command's unique ID and expected revision are checked, or the handshake's message shape, and no such code exists. No `Campaign`, `Manifest`, or domain command type exists either, so this cannot implement a real command; it specifies the protocol contract those will eventually run over, the same way [M0a criterion 4](../development-plan.md#milestones) specifies cross-package set operations without implementing them. `CanonicalWriter`/`CanonicalReader` ([decision 0020](0020-canonical-encoding-and-content-hash.md)) exist and are the versioned encoding decision 0027 names; this is their first caller outside their own tests.

## Decision

**Protocol version.** `ProtocolVersion.Current = 1` in `SpaceExplorer.Core.Networking`, a `uint`. A separate axis from `CanonicalWriter.FormatVersion` and `GeneratorVersion`, for the reason [decision 0020](0020-canonical-encoding-and-content-hash.md) gave for those two: save format, generator, and protocol compatibility change independently.

**Transport.** `ITransport` has exactly the four members [decision 0003](0003-network-topology-and-transport.md) names: `Send(PeerId to, ReadOnlyMemory<byte> payload)`, and the events `Received`, `PeerConnected`, `PeerDisconnected`. Every member is peer-addressed, so a transport that later supports more than one simultaneous peer needs no interface change, matching decision 0003's "adding guests is a capacity and testing question rather than a protocol change." `InMemoryTransport` is the M0a implementation: a 1:1 pair, matching "the core release supports one guest." A pair is built by creating each side (`Create(PeerId)`) and connecting them (`ConnectTo`) as two separate steps, not one combined factory, so a caller that subscribes to `PeerConnected` after construction but before connecting never misses the event; connecting inside one factory call would fire it before any subscriber existed to hear it. `Send` to an unconnected transport, or naming any peer but the one connected, throws; `Disconnect` fires `PeerDisconnected` on both sides and blocks further sends.

**Command journal.** `CommandJournal`, named apart from the save's HMAC-chained transaction ledger ([decision 0018](0018-data-root-region-encoding-and-save-integrity.md)) so the two are never confused. It tracks one counter, `CurrentRevision`, and one map from `CommandId` to the result bytes recorded for it. A `(CommandId, expectedRevision)` is acceptable only when the ID has no recorded result yet and `expectedRevision` equals `CurrentRevision`; recording a result advances `CurrentRevision` by exactly one. Resubmitting a recorded ID is a replay: the journal returns the stored result bytes instead of accepting it again, which is "commands carry unique IDs... retried commands return their original results" (technical design, artifact valuation and transactions) implemented as a mechanism, not yet applied to any real command. The journal knows nothing about what a result means; it stores whatever bytes the caller recorded.

**Join handshake.** `JoinRequest` (protocol version, peer ID, campaign ID, a manifest list, and the sender's state revision) and `JoinResponse` (`Accepted(hostRevision)` or `Rejected(reason)`) are canonically encoded under their own domain labels, `join-request/1` and `join-response/1`. `JoinHandshake.Evaluate` checks, in order, the protocol version, the campaign ID, and that every requested manifest is one the host has, rejecting on the first mismatch with a reason identifying which check failed. This is "reject unsupported combinations explicitly" (technical design, multiplayer and trust boundary) as a mechanism a real join can call once a real campaign and manifest set exist.

**What is deliberately not decided.** Campaign identity has no design yet, so `JoinRequest.CampaignId` is typed as a placeholder `ContentHash`; manifests are a placeholder `PackId` list. Both exercise the handshake's shape, not a decision about what a campaign or a manifest is. `CommandId` is an opaque `ulong` wrapper with no issuing mechanism here: `Guid.NewGuid` and `System.Random` are rejected in Core at build time ([decision 0008](0008-random-stream-derivation.md)), so a real issuer (for instance a per-peer sequence number) is a later caller's problem, not this one's. The Godot/ENet adapter over `ITransport` stays out of scope until M1 start (the connectivity approach) and M2 start (the first mixed-OS connection), per decision 0003.

## Consequences

Easier: the mitigation decision 0003 named, in-memory transport tests from M0a onward, now has a transport, a command mechanism, and a handshake to test; a future real command or campaign only has to supply its own payload and identity types, not redesign the envelope around them. Harder: three new frozen wire shapes exist before any code sends real game data over them, so a shape that turns out wrong once `Campaign` or a domain command lands is a protocol-version increment, not a free edit.

Verified: `dotnet build` with zero warnings; the full suite passes locally; the `Networking` suite is mutation-checked on the connect-before-subscribe ordering in `InMemoryTransport` and the revision-versus-replay branch in `CommandJournal`, each of which turns it red. Verified by the Multiplayer check and M0a exit criteria in the [development plan](../development-plan.md#verification-and-performance-targets); [progress.md](../progress.md#m0a-exit-criteria) tracks it.
